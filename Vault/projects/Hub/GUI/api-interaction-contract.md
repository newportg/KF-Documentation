# API interaction contract

This document records what replacement screens need from the server. It is
not an OpenAPI specification; the generated client remains the detailed
method-level endpoint inventory.

## Request model

The UI constructs requests from:

- route parameters and parent entity identifiers;
- search criteria, filters, sort, paging, selected columns, and map bounds;
- reactive form values and selected lookup records;
- current user and, where applicable, proxy-user context;
- runtime configuration such as the API root and localization settings.

The effective REST shape is generally:

```text
{runtime rootUrl}/api/{resource}/{operation}[/{id}][/{sub-resource}]
```

## Operation families

| Operation | Typical use |
|---|---|
| `GET /{resource}/{id}` | Load a detail or profile |
| `GET /{resource}/{id}/preview` | Load a lightweight preview |
| `GET /{resource}/{id}/editData` | Load edit data and lookup context |
| `POST /{resource}/search` | Execute a paged search |
| `POST /{resource}` | Create a record or command |
| `PUT /{resource}/{id}` | Update a record |
| `DELETE /{resource}/{id}` | Delete or remove a record/association |
| `POST /{resource}/{id}/activities` | Query or create related activities |
| `POST /{resource}/{id}/notes` | Create or query related notes |
| `POST /{resource}/{id}/attachments` | Upload or attach documents |
| `DELETE /{resource}/{id}/attachments/{attachmentId}` | Remove an attachment |
| `POST /{resource}/{id}/stateValidate` | Validate a candidate state transition |
| `PUT /{resource}/{id}/parties` | Update people or party relationships |
| `PUT /{resource}/{id}/addresses` | Update addresses |
| `POST /activities/matches/{id}` | Manage activity/requirement matching |
| `POST /activities/{id}/termsAndConditions` | Manage activity terms |
| `POST /viewings` | Create or update a viewing |
| `PUT /viewingtours` | Update a viewing tour |
| `POST /widgets/{area}` | Load dashboard widget data |
| `POST /widgets/{area}/drilldown` | Load widget drill-down data |
| `GET /attachments` and related operations | List and manage documents |
| `GET /wopi/files/{fileId}` | Online document content interaction |
| `GET /watermarks/{entityId}` | Image/document processing support |

## Service groupings

Replacement screens need equivalent server capabilities for:

- activities, appointments, offers, and requirements;
- contacts, consent, and callback lists;
- companies, businesses, ownership, and property hierarchy;
- properties, buildings, developments, estates, phases, and portfolios;
- tenancies, progression, renewal, termination, paperwork, and Qube;
- attachments, document templates, WOPI, watermarks, and portal visibility;
- emails, text messages, notifications, notes, and external messages;
- dashboards, widgets, saved searches, latest views, and preferences;
- users, departments, configuration, translations, subscriptions, and Dotmailer;
- reports, publication events, Thirdfort, web enquiries, and other
  integrations.

## Response behavior required by the UI

Responses need to communicate more than a record payload:

- typed detail, preview, search-result, and edit-data models;
- paging totals and result rows;
- lookup and enum values;
- validation failures and status-specific required fields;
- authorization failures;
- command success/failure and user-readable messages;
- updated identifiers and refresh requirements;
- attachment upload progress and metadata;
- notification, publication, and integration outcomes where relevant.

## Authority boundaries

The client owns presentation behavior and immediate form validation. The
server remains authoritative for:

- authorization;
- entity existence and concurrency;
- state-transition validity;
- cross-entity business rules;
- persistence;
- integration outcomes;
- document permissions and visibility.

The replacement must preserve these boundaries even if its client technology
changes.
