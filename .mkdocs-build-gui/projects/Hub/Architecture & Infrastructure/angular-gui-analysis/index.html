    Angular GUI analysis

    Source analysed: C:\Source\Devops\KnightFrank.hub\src\KnightFrank.Antares.Angular
    Status: Source-derived baseline; SME and UX validation remain outstanding
    Last reviewed: 2026-11-17

    Purpose and scope

    This document describes the Hub Angular GUI down to the relationship between:

    1. application shell and navigation;
    2. lazy-loaded feature areas and screen families;
    3. domain entities and user processes;
    4. forms, validators, guards, resolvers, and HTTP interceptors;
    5. generated API clients, HTTP verbs, URL patterns, request models, and response models; and
    6. screen layout patterns and reusable UI services.

    The analysis is based on the Angular source. It describes implemented structure, not necessarily approved business behaviour. The API client under src/app/autogenerated is generated code and should be treated as the canonical endpoint inventory.

    Application structure

    Bootstrap and shell

    Layer Source location Responsibility
    Angular application src/main.ts, src/app/app.component.ts Bootstraps the application and root component.
    Root module src/app/app.module.ts Registers routing, translation, HTTP, interceptors, Material defaults, notifications, and the authenticated layout.
    Route table src/app/app-routing.module.ts Redirects the root to dashboard, protects the main shell, and lazy-loads feature modules.
    Application shell src/app/layout/ Provides the common navigation, page frame, menus, route outlet, and shared layout services.
    Generated API module src/app/autogenerated/api.module.ts Registers generated domain and integration API services.
    Configuration src/app/config/, src/app/providers/, src/app.json Loads runtime configuration and administration screens.
    Shared UI src/app/common/, src/app/shared/, src/app/services/ Reusable controls, dialogs, tables, selectors, attachments, notes, notifications, and utility services.

    Screen and layout patterns

    Feature folders consistently use a small number of screen patterns:

    Screen pattern Typical implementation Layout/API behaviour
    Search/list *-search components Criteria form → paged query → grid/table → preview or view navigation.
    Add/edit *-add, *-edit, *-add-edit components Resolver loads edit data → reactive form → validation → create/update command.
    View/profile *-view, *-preview-panel components Load summary/detail model → tabs/cards/panels → related entity queries and commands.
    Relationship panel *-activities, *-contacts, *-requirements, ownership/tenancy panels Parent ID drives child query; actions open related screens or update associations.
    Modal/panel workflow *-panel, *-modal, *-dialog components Focused command, confirmation, validation, upload, or preview without leaving the parent screen.
    Publication/marketing publication/, marketing panels, image and brochure controls Load publication state → validate → save/publish/unpublish → refresh status.
    Administration Administration feature submodules Role-protected configuration lists and edit dialogs.

    The visual system is based on Angular Material/CDK, Bootstrap, Font Awesome, FullCalendar, Gridstack, Google Maps, Froala, ngx-mat-select-search, and ngx-toastr. Translation is provided by @ngx-translate. Shared defaults for forms, paginator behaviour, dialogs, tabs, select controls, and toast messages are registered in app.module.ts.

    User process layouts

    Search to detail

    Route entry
  -> feature search component
  -> criteria form and lookup data
  -> generated query service (POST search endpoint)
  -> pageable result/grid
  -> preview panel or detail route
  -> related tabs and child API calls

    Add or edit

    Route / resolver
  -> edit-data query (GET)
  -> reactive form population
  -> field and cross-field validation
  -> user confirmation
  -> generated create/update command (POST or PUT)
  -> toast/error handling
  -> route refresh or return to parent

    State-changing workflow

    View or edit screen
  -> validate command or state transition (POST .../stateValidate or domain equivalent)
  -> confirmation modal
  -> state/update command (PUT or POST)
  -> refresh detail model, activity feed, and related projections

    Attachments and documents

    Entity screen
  -> attachment list/details query
  -> upload or document command
  -> attachment type/visibility/version command
  -> optional WOPI/signing operation
  -> refresh attachment list and entity state

    Validation and access control

    Route and application validation

    • authorizeGuard protects the authenticated application shell.
    • roleAuthorizeGuard restricts administration and configuration routes.
    • Resolvers load required configuration and edit data before rendering.
    • RedirectComponent, not-found, and no-access handle invalid or unauthorized navigation.
    • Route reuse and dynamic anchor scrolling are handled by shared services.

    Form and business validation

    Feature components use Angular reactive forms (FormBuilder, FormGroup, FormControl, and Validators) for field-level validation. Domain-specific validation is additionally represented by:

    • edit-data and lookup resolvers;
    • generated API command/result types;
    • dedicated validation endpoints, including activity state validation;
    • confirmation modals before destructive or irreversible commands;
    • server error responses surfaced through the shared error interceptor.

    The source analysis should distinguish client-side validation from server-side business validation; passing a form does not establish that a domain command will be accepted.

    HTTP cross-cutting behaviour

    app.module.ts registers:

    • KfXssInterceptor for request/response XSS handling;
    • KfErrorInterceptor for shared API error handling;
    • DateAttributesInterceptor for date conversion;
    • ProxyUserInterceptor for proxy-user context;
    • Angular HttpClient with DI interceptors and JSONP support.

    API call layout

    Generated client contract

    Generated services live in src/app/autogenerated/api/. Each service:

    1. injects Angular HttpClient and AppConfigProvider;
    2. creates basePath as ${configProvider.appConfig.rootUrl}/api;
    3. exposes typed methods with generated request interfaces;
    4. serializes query/body/path parameters;
    5. calls a REST endpoint using GET, POST, PUT, or DELETE; and
    6. returns a typed model, query result, command result, or Observable<HttpEvent<T>>.

    The effective URL shape is therefore:

    {runtime rootUrl}/api/{resource}/{operation}[/{id}][/{sub-resource}]

    Embedded business rules

    The Angular code contains material business behaviour. It is not only a presentation layer. The rules fall into two categories: client-side rules that shape the screen and request, and server-backed rules that the GUI asks the API to validate.

    Confirmed client-side rules

    Rule area Embedded behaviour Evidence
    Status defaults Instructed and marketed dates are defaulted when configured activity statuses are entered, including a market-appraisal-to-sale transition. common/helpers/activity-default-dates.helper.ts
    Status display and filtering Active status groups, ordering, and default filters are encoded in a shared service. common/services/activity-status.service.ts
    Offer status eligibility Reservation offers are limited to Reserved and Withdrawn; offer status options vary by offer type. common/services/offer-status.service.ts
    Offer calculations Accepted offers default agreed price from offer price; area-based amounts and annual amounts are converted; lease end dates are calculated from week/month periods. offer/offer-add-edit/offer-add-edit.component.ts
    Lease dates Lease terms are capped against remaining lease duration and invalid, expired, inverted, or null dates are rejected. common/helpers/lease-date-helper.ts
    Activity and requirement status panels Notes, completion dates, exchanged dates, lost-to information, and negotiator controls appear conditionally for selected statuses. common/attributes/status-change/entity-status-control/entity-status-control.component.ts
    Referral and publication behaviour Referral requirements and Feed Centre unpublishing are selected from hard-coded activity status sets. activity/activity-add-edit/activity-add-edit-base.component.ts
    Ownership changes Completion ownership options vary by completion/letting status, agency type, service line, accepted offer, applicant/requirement presence, and ownership type. common/attributes/status-change/completion-ownership-control/completion-ownership-control.component.ts
    Instruction linking Requirement instruction actions differ when the requirement is withdrawn or when an instruction already exists. requirement/requirement-view/requirement-view.component.ts
    Field constraints Required fields, maximum lengths, non-negative amounts, and minimum positive rent values are encoded in form schemas and controls. activity/activity-add-edit-common/activity-add-edit-common.schema.ts, feature form components
    Route permissions Administration and configuration screens are limited by route role lists. app-routing.module.ts, common/guards/role-authorize.guard.ts

    Server-backed rules initiated by the GUI

    Before changing an existing Activity or Requirement status, the status control calls the API validation operation. Activity validation includes service line, agency, activity type, CDD state, instructed date, rent data, matching/resale flags, lease completeness, image/brochure presence, and managing department. The API also returns status-specific requirements such as whether a note, completion date, exchanged date, lost-to information, or negotiator restriction applies.

    Representative calls are:

    POST /api/activities/{id}/stateValidate
POST /api/requirements/{id}/stateValidate

    The GUI then opens the required panels, applies client-side form checks, and submits the state/update command. A valid Angular form therefore does not prove that a business transition is valid; the API validation remains authoritative.

    Hard-coded domain vocabularies

    The client contains status and lifecycle values used to drive controls and visibility, including:

    • Activity: PreAppraisal, MarketAppraisal, ForSaleOnMarket, UnderOffer, Exchanged, Completed, Withdrawn, and Lost.
    • Offer: New, Accepted, Rejected, Withdrawn, UnderOffer, and Reserved.
    • Requirement: Active, UnderOffer, Satisfied, Withdrawn, and Lost.
    • Referral: New, Accepted, Instructed, Completed, and Finished.
    • Instruction: Potential, Instructed, Aborted, Finished, and Disinstructed.

    The source of these values is common/models/enums/enum-type-items.ts. They should be checked against the API/domain enums during SME review because client values can become stale.

    Classification

    Classification Examples Documentation treatment
    Client-enforced Required fields, length/amount bounds, date calculations, visibility, default values, route guards Record as GUI behaviour; do not assume it is sufficient security or domain enforcement.
    Server-backed Activity/Requirement transition validation, status-specific requirements, save/update commands Record the API call and treat the server response as authoritative.
    Inferred from UI Status grouping, panel sequencing, derived offer display values Mark as implementation evidence until confirmed by an SME or server contract.

    Traceability and limitations

    • Route structure is evidenced by src/app/app-routing.module.ts.
    • Application providers and interceptors are evidenced by src/app/app.module.ts.
    • API service registration is evidenced by src/app/autogenerated/api.module.ts.
    • Endpoint paths and HTTP verbs are evidenced by src/app/autogenerated/api/*.service.ts.
    • Embedded business-rule evidence is evidenced by the status-control, activity/offer/requirement workflow, helper, enum, and validation files cited above.
    • Screen layout patterns are evidenced by the feature component folders and their templates.
    • This document does not claim that every generated endpoint is used by a visible screen; some services support integrations, background workflows, administration, or future screens.
    • UX labels, field ordering, responsive breakpoints, and business approval require review of the HTML/SCSS templates and an SME or product owner.
