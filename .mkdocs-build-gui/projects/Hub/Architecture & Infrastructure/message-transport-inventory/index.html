    Production naming convention

    The physical Azure entity names follow the Microsoft Cloud Adoption Framework (CAF) naming convention. In practice, the production form retains the entity, workload, region, and instance components and changes only the environment component from local or dev to prd where that component is present. For example, a sbt-activity-local-ee value would become sbt-activity-prd-ee, subject to the deployment template's exact token placement.

    Production validation should therefore confirm:

    • the deployment parameters or environment settings that replace the local/dev environment token with prd;
    • that the entity, workload, region, and instance components remain unchanged;
    • that the injected names match the infrastructure definitions and CAF naming convention; and
    • whether any service-specific abbreviations or legacy exceptions are approved.

    The checked-in local-ee and dev-ne values above are dev/local names only and must not be presented as production names.

    Message contract

    HubServiceBusTopicMessage<T> carries:

    • Topic;
    • PublishEventType;
    • typed MessageData;
    • optional CustomMetadata;
    • optional SessionId.

    HubServiceBusPublisherSubject represents an entity type and publish event type using string-enum JSON conversion.

    The common Azure storage layer exposes queue clients and wrappers. The queue names above are the configured dev/local values. Production entity names are injected at deployment and are expected to follow the Microsoft CAF naming convention. Poison-message handling, retry counts, visibility timeouts, and deployment settings still require environment-level review.

    Processing pattern

    1. A controller, domain service, timer, webhook, or integration publishes a message
    2. Azure Storage Queue or Service Bus delivers the message to the WebJobs host
    3. A feature module resolves a handler through the dependency-injection container
    4. The handler validates and processes the message
    5. The handler writes to SQL, Blob Storage, Elasticsearch, or an external service
    6. Failures are logged and rethrown in the inspected Thirdfort handlers, allowing the host's configured retry behaviour to apply

    Required follow-up

    • Extract physical names from environment templates and deployment parameters.
    • Map each topic to subscriptions and consumer modules.
    • Record retry count, visibility timeout, dead-letter/poison handling, and idempotency behaviour.
    • Identify message versioning and compatibility rules.
    • Document retry/error policies for each handler (some use host retry, others implement custom retry logic).
